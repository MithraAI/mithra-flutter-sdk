## 0.0.0

`0.0.0` is the pre-publication baseline recorded in
`.release-please-manifest.json`, not a released version -- nothing was ever
published under it. The notes below describe the API surface the package was
built with before its first release, so the first generated section above is a
delta against this baseline rather than against an earlier release.

This heading is deliberately version-shaped, because it is also the anchor
release-please inserts before: its changelog updater searches for the first
heading matching `\n###? v?[0-9[]` and prepends the new section there. With a
non-numeric heading it finds none, and then re-stamps its own `# Changelog`
title and demotes this file's headings by one level on every release.

### Added

- Initial Flutter plugin, published as **`mithra_flutter_sdk`**, bridging the
  Narya native SDKs (`narya-ios` 1.3.x and `narya-android` 1.3.x). The public
  Dart API keeps the `Narya` product naming (`Narya`, `NaryaConfiguration`,
  `NaryaException`, ...); only the package, plugin and module identity uses the
  `mithra_flutter_sdk` name.
- Requires **Dart `^3.11.0`** and **Flutter `>=3.41.0`** - the current Flutter
  stable and the two preceding stable releases (3.47.x / 3.44.x / 3.41.x at the
  time of this release).
- A **single, cross-platform `writeKey`**: `NaryaConfiguration` takes one
  required `writeKey` (wire field `writeKey`) that both the iOS and the Android
  build use. There are no per-platform `iosWriteKey` / `androidWriteKey`
  fields and no per-platform "missing key" error path; `missing_write_key` is
  raised only when `writeKey` is empty.
- iOS ships through **CocoaPods by default with zero configuration** - the
  podspec's `prepare_command` downloads and checksum-verifies the pinned
  `MithraAnalytics.xcframework` during the `pod install` that `flutter run`
  performs. **Swift Package Manager is opt-in** and pins the same native SDK
  version.
- Core analytics: `Narya.initialize`, `identify`, `track`, `screen`, `group`,
  `alias`, `flush`, `reset`, `startSession`, `endSession`, `openUrl`,
  `shutdown`, and the `anonymousId` / `userId` / `traits` / `sessionId`
  accessors.
- `NaryaConfiguration`, `NaryaSessionConfiguration` and
  `NaryaInAppConfiguration` with `NaryaEnvironment` selection and an explicit
  `dataPlaneUrl` override.
- Push bridge `Narya.push`: token registration, received / opened tracking,
  deep-link resolution, background notification handling on iOS, cold-start
  payload retrieval, and the `onPushOpened` stream.
- `Narya.push.isNaryaPush(payload)`: a pure-Dart, synchronous gate that tells
  whether a raw `firebase_messaging` / APNs payload was sent by Mithra, mirroring
  the reference SDK's `isIterablePush`. It needs no `Narya.initialize` and no
  platform channel, so it is safe in the background isolate. The rule matches
  the native SDKs byte for byte: on any of the root / `CustomData` / `mithra`
  levels, a non-empty `tracking`, a truthy `inapp_sync` or a non-empty
  `mithra_message_id` qualifies, as does a top-level `mithra` key holding a
  JSON object; a bare `message_id` / `gcm.message_id` does not.
- In-app and inbox bridge `Narya.inApp`: message and inbox queries, read and
  delete state, imperative display, sync, auto-display pausing, the json-only
  replay buffer, inbox session and impression tracking, delegate hooks, and the
  displayed / dismissed / inbox-changed / unread-count streams.
- `NaryaRouteObserver` for Flutter route-based screen tracking.
- **Android notification rendering from Dart**:
  `Future<bool> Narya.push.handlePushMessage(Map<Object?, Object?> data,
  {NaryaPushDisplayOptions options})`. Mithra sends data-only FCM messages, and
  a Flutter Android app previously had no way to reach the native SDK's
  renderer, so it showed **no notification** (and no action buttons) for a
  Mithra push. The new method calls the native `Analytics.handlePushMessage`
  with a `PushDisplayOptions`, exactly as the native Android demo's
  `FirebaseMessagingService` does: `push_delivered` is tracked and the
  notification is posted with title, body, image, action buttons and channel;
  taps keep flowing to `onPushOpened` / `takeInitialPushPayload`. Returns
  `true` when a notification was posted and `false` for silent payloads
  (including the `inapp_sync` wake push, which still triggers the in-app sync).
  iOS returns `false` and does nothing: the NSE renders there. Call it from
  **both** `FirebaseMessaging.onMessage` and `onBackgroundMessage`.
  The new exported `NaryaPushDisplayOptions` (`smallIcon` resource name,
  `tapActivity` class name, `channelId`, `channelName`; all optional) mirrors
  the native `PushDisplayOptions`; the small icon defaults to the application
  icon and the tap activity to the launcher activity.
- Android: the native `Analytics` instance is now **process-wide** (shared by
  every Flutter engine's plugin instance) and the last successful
  `NaryaConfiguration` is persisted to `SharedPreferences` on `initialize`.
  `push.handlePushMessage`, `push.trackReceived` and `push.trackOpened` restore
  the SDK from it when called in a process where `Narya.initialize` never ran -
  the `firebase_messaging` background isolate after an FCM cold start - logging
  one debug line. `not_initialized` is now raised by those three only when no
  persisted configuration exists; `shutdown` clears it. A same-configuration
  `initialize` that finds the restored instance adopts it and installs the
  engine's in-app hooks.
- **Native APNs registration on iOS** (Iterable parity: no `firebase_messaging`
  needed to get a push token).
  `Narya.push.registerForRemoteNotifications({alert, badge, sound})` requests
  `UNUserNotificationCenter` authorization with the given options and, when
  granted (or already authorized / provisional), calls
  `UIApplication.registerForRemoteNotifications()` on the main thread. It
  returns the new `NaryaPushAuthorizationStatus` enum (`authorized`,
  `provisional`, `denied`, `notDetermined`, `unsupported`). The iOS plugin now
  registers itself as a Flutter application delegate: the APNs token is handed
  to the native SDK (`setPushToken(deviceToken:)`) with no host code - queued
  when it arrives before `Narya.initialize` and applied on initialization - and
  emitted as a lowercase hex string on the new `Stream<String>
  Narya.push.onToken`; a registration failure is emitted on the new
  `Stream<NaryaPushRegistrationError> Narya.push.onRegistrationError`
  (`code`, `message`). Silent remote notifications delivered to the app
  delegate are forwarded to the SDK's `handleBackgroundNotification` (in-app
  sync wake) and visible Mithra pushes reaching it are tracked as delivered.
  `registerForRemoteNotifications` also installs the plugin as the
  `UNUserNotificationCenter` delegate, chaining to whatever delegate was
  installed before (see Fixed below):
  foreground pushes are presented (`banner`, `list`, `sound`, `badge`) and
  tracked as `push_delivered` when `Analytics.isNaryaPush` says so (skipped if
  a Notification Service Extension already tracked them), and taps flow through
  `trackPushNotificationOpened(response:)` into the existing `push_opened`
  event / `takeInitialPushPayload` cold-start capture; a tap received before
  `Narya.initialize` is replayed after it. New event-channel envelope types
  `push_token` (`{token}`) and `push_registration_error` (`{code, message}`).
  On Android the method returns `unsupported` and the streams never emit:
  Android tokens come from FCM through `Narya.push.setToken`, unchanged.
  Call `registerForRemoteNotifications` only if the Narya SDK should own APNs
  registration on iOS; hosts that keep `firebase_messaging` in charge of iOS
  APNs use `setToken` instead. The two token paths are never combined.
- **App icon badge control**: `Future<void> Narya.push.setBadgeCount(int count)`
  and `Future<void> Narya.push.clearBadge()` (exactly `setBadgeCount(0)`).
  gwaihir stamps `badge = 1` on every alert push it sends and no payload ever
  sets the badge back to zero, so on iOS the app icon badge lit up on the first
  notification and then **stayed lit forever**: APNs changes the badge only
  when a payload sets it, and a Flutter host had no bridged way to reset it.
  On iOS the bridge calls
  `UNUserNotificationCenter.setBadgeCount(_:withCompletionHandler:)` on
  iOS 16+ and falls back to `UIApplication.applicationIconBadgeNumber` on
  iOS 15, both on the main thread; a system failure surfaces as a
  `NaryaException` with code `badge_failed`. On **Android** the call is a
  documented no-op that logs one debug line and returns normally - Android has
  no platform app-icon badge API, launchers derive the dot or count from the
  notifications the app currently has posted - so host code needs no
  `Platform.isIOS` branch. A negative count is clamped to `0` on all three
  layers. Neither call needs `Narya.initialize`: the badge is platform state,
  not SDK state, so a badge left over from a previous launch can be cleared
  before the SDK is configured. The SDK deliberately **never** touches the
  badge on its own - not when it renders a push, not at start-up, and not when
  the inbox unread count changes; an app that wants badge-follows-inbox wires
  it itself by feeding
  `Narya.inApp.onUnreadInboxMessageCountChanged` (plus one
  `Narya.inApp.unreadInboxMessageCount` read at start-up) into
  `setBadgeCount`, and picks that *instead of* a resume-clear so the two do
  not fight.
- `Narya.inApp.onDeepLink`: a broadcast `Stream<NaryaInAppDeepLinkEvent>`
  (`url`, `messageId`) that delivers every ordinary link tapped inside an
  in-app message to the host as a distinct callback, Iterable-style. The SDK
  never opens the URL; the host routes it. New event-channel envelope type
  `inapp_deep_link`.

### Fixed

- iOS: `registerForRemoteNotifications` never became the
  `UNUserNotificationCenter` delegate in a real Flutter app, so foreground
  pushes were not tracked as `push_delivered` and taps never reached
  `onPushOpened` / `takeInitialPushPayload`. The plugin only took the role when
  no delegate existed, but `FlutterAppDelegate` is the delegate at launch and
  forwards only the `UIApplicationDelegate` APNs callbacks to plugins, not
  `willPresent` / `didReceive(response:)`. Third-party delegates never forward
  either: an app that links `firebase_messaging` for Android still gets
  `FLTFirebaseMessagingPlugin` installed as the iOS delegate, which swallowed
  the callbacks so foreground pushes showed no banner and were not tracked.
  The plugin now **always** takes the delegate over when
  `registerForRemoteNotifications` is called (unless it already holds it),
  keeps a weak reference to the replaced delegate - `FlutterAppDelegate`, a
  host object or `firebase_messaging` alike - and forwards `willPresent`
  (presentation options merged), `didReceive(response:)` (previous delegate
  completes) and `openSettingsFor` to it after its own handling, guarding
  against the `FlutterAppDelegate` fan-out echo and logging one debug line
  that names the chained delegate class. The delegate is installed
  synchronously even before `Narya.initialize`, so a cold-start tap is
  captured and replayed on initialization.
- In-app message deep links were lost on both platforms. On Android the bridge
  never registered an `InAppDeepLinkHandler`, so the native SDK logged "no deep
  link handler registered" and dropped the link. On iOS the native SDK funnels
  in-app links through the push-open handler, and the bridge forwarded them as
  a `push_opened` event with an empty payload, so hosts could not tell them
  from a push and any `isNaryaPush` gate discarded them. Both now surface on
  `Narya.inApp.onDeepLink`; `push_opened` is reserved for real pushes.

### Documentation

- `NaryaPushOpenEvent`, the README and `docs/api-contract.md` now state that
  SDK-delivered events (`onPushOpened`, `takeInitialPushPayload`,
  `onDeepLink`) are already Mithra-originated and must not be gated with
  `isNaryaPush`, which is for raw `firebase_messaging` / APNs payloads only.
